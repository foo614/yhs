# WhatsApp template dispatch continuation

Continue the existing notification ticket after its default-disabled capture/admin release. Implement sending for the three already captured customer events (enquiry, loan update, receipt notification). Staff reminder assignment and the role-scoped assistant remain separate unfinished work.

- Require explicit capture/sending switches, reviewed sender/template approval evidence, a positive daily attempt cap, monthly budget in sen, a reviewed conservative per-attempt cost ceiling and a named budget owner. Missing configuration prevents dispatch. No real template approval or tariff is invented.
- Match the exact draft key and BM/English language to an approved provider template, send only one bounded reference parameter, and never send stored free-text bodies. No document delivery is added.
- Claim one event and reserve daily/monthly usage in a short database transaction shared by all workers. Keep reservations for rejected/unknown requests. Never send inside the business mutation transaction. Recheck consent, receipt validity and expiry before submission.
- Bound requests, disable HTTP retries/redirects, distinguish acceptance from delivery, retry only explicit rate rejection up to three attempts, and hold ambiguous failures for review. Retain attempt ownership when a lease expires.
- Host a separately gated API worker and signed opt-out/status callback endpoint. Customer STOP revokes consent and suppresses pending work; no business-query assistant or general inbound replies are added.
- Verify provider payload/redaction, disabled and missing-approval behavior, cap/budget exhaustion, competing workers, consent withdrawal, receipt voiding, unknown outcomes and signed callbacks. Reuse backend suites and the isolated PostgreSQL CI service. Run focused checks, broader backend/UI checks, independent diff review and required CI before a default-disabled release.

Production sending/capture are not enabled by this change. Actual template approval, sender approval, budget owner and amount remain operator decisions before activation. No customer or financial records are manufactured in production. Local tests and CI use synthetic data and mock provider responses.

## Operator configuration and activation boundary

All configuration lives under `WhatsApp`. `CaptureEnabled`, `SendingEnabled` and `WebhookEnabled` default false. Sender activation additionally requires a valid `GraphApiVersion`, `PhoneNumberId`, `BusinessAccountId`, server-only `AccessToken`, `AppSecret` and `VerifyToken`; `SenderApproved` with bounded `SenderApprovalEvidence`; `DailyAttemptLimit`; `MonthlyBudgetSen`; `MaximumCostPerAttemptSen`; `CostCeilingConfirmed`; and `BudgetOwner`. No tariff or budget is selected by the code. The per-attempt ceiling must be reviewed for the approved category/recipient market; these counters reserve an operator-supplied conservative ceiling, not measured provider invoices. Calendar counters use Malaysia time. Lowering a limit applies on restart without clearing usage.

`Templates` is an operator-reviewed approval manifest. Each entry requires `Key` (one of the three draft keys), exact `Language` (`ms` or `en_US`), actual approved provider `Name`, `Approved=true`, and `ApprovalEvidence`. Duplicate key/language mappings or an invalid entry disable the worker. Configuration assertions must be checked against the selected sender's real Meta approval before activation; the engine does not submit templates or infer approval from a draft name.

The public signed callback is `/api/whatsapp/webhook`; it remains inactive until callback configuration and capture are valid. Connect it only during the separately reviewed activation step; this development does not replace the existing test-probe callback. GET validates the verification token. POST checks the raw-body HMAC, WABA and sender IDs before accepting STOP/BERHENTI or statuses for known accepted messages. Unrecognized messages are ignored; a status arriving during acceptance requests a provider callback retry without persisting its raw body.

The global budget row lock is released before HTTP. A per-recipient consent lock and, for receipt notifications, a receipt-validity lock remain for the bounded provider request. Withdrawal or receipt voiding concurrent with an already authorized submission waits for that request to settle; an already submitted message cannot be recalled. Provider timeout/transport failure is UnknownOutcome and must be reviewed, not replayed. Known HTTP 429 errors retry at 30/120 seconds up to three attempts; other valid 4xx errors require an eligible audited manual retry. Provider 5xx or malformed responses are not retried. Worker cadence is five seconds. Missing approvals/budget/callbacks stop dispatch before touching the database.

Schema additions are `WhatsAppDispatchUsage` and `WhatsAppOutbox.TemplateReference`; setup remains gated by capture. Old drafts without a dedicated safe template reference stay held, with no implicit backfill/replay. The separate test probe has only an additive reference-column compatibility upgrade; its dispatcher never sends business templates.

Remaining ticket scope: approved real sender/templates and operating budget, production activation, verified staff assignment/reminders, authenticated receipt-document delivery, complete business HTTP smoke, and retention execution. No destructive retention job or staff binding is added by this continuation.

Primary provider contract: [Meta's official WhatsApp collection](https://www.postman.com/meta/whatsapp-business-platform/overview), [template components](https://www.postman.com/meta/whatsapp-business-platform/request/lwtlz1k/send-message-template-interactive), and [webhook subscription setup](https://www.postman.com/meta/whatsapp-business-platform/folder/ozgs3jn/webhook-subscriptions).
